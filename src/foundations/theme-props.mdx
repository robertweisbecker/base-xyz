# Theme props

Theme props are typed, token-backed layout controls. This is the pattern often called **system props** or **style props** in other design systems. Use them for local composition changes; use the final `style` prop when the supported contract cannot express the design.

## Values

| Family           | Values                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Spacing          | `0, 0.5, 1, 1.5, 2, 3, 3.5, 4, 5, 6, 7, 8, 9, 10, 12, 16`                                                              |
| Margin and inset | Spacing steps, negative steps, or `auto`                                                                               |
| Padding and gap  | Nonnegative spacing steps                                                                                              |
| Width            | Spacing steps, `full`, container sizes, CSS strings, or `1/2`, `1/3`, `2/3`, `1/4`, `3/4`                              |
| Other dimensions | Spacing steps, container sizes, `auto`, `full`, `min-content`, `max-content`, `fit-content`, `stretch`, or CSS strings |

Numeric values always mean token steps. Inline spacing and position use logical names: `ms`/`me`, `ps`/`pe`, and `insetStart`/`insetEnd`.

## Component coverage

| Surface                           | Theme props                                                                                               |
| --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Box                               | Display, spacing, sizing, position, child layout, spans, semantic colors, radius, shadow                  |
| Stack                             | Box plus orientation, reverse, alignment, distribution, wrapping, and gaps                                |
| Grid                              | Box plus 1–12 columns, flow, alignment, gaps, and child spans                                             |
| Card                              | Scalar non-color Stack composition, radius, and shadow                                                    |
| EmptyState                        | Non-color Stack composition                                                                               |
| Card header/footer                | Stack distribution and spacing, retaining their component defaults                                        |
| Card content                      | Logical spacing, sizing, position, and child layout                                                       |
| Card title/description            | Logical margins and text alignment                                                                        |
| Text and Heading                  | Logical margins and text alignment; their existing semantic text color remains separate                   |
| Button, IconButton, Toggle, Badge | Root padding/gap, margin, sizing, position, and child placement                                           |
| Separator                         | Margin, sizing, position, and child placement                                                             |
| Field wrappers                    | Non-color Stack layout on the public wrapper only; inner control geometry and chrome stay component-owned |

Shared `color` and `bg` are intentionally unavailable on non-layout components. Theme props are scalar on every component, including layout primitives. Existing component-owned APIs such as Text `color`, Badge `hue`, and variants remain authoritative. Component families assemble their public interfaces and runtime definitions from reusable capabilities such as `FlexProps` and `SurfaceThemeProps`; the shared module does not own component contracts. Token-backed value unions are derived from the corresponding token keys where possible.

Public value and capability contracts, StyleX-independent resolution, and the spacing/text, layout, and surface compilers live under `src/theme`. The compilers remain explicit StyleX modules; consumers import only the capabilities they use. Runtime key tuples exactly match their public capability interfaces, duplicate keys are rejected during composition, and only compiler leaves with active props run.

All themeable StyleX values share one typed public interface. Component styles
import `tokens` directly and address its stable named variables; theme-prop
values remain semantic variants that map onto this same contract.

```tsx
import { tokens } from "@/theme/tokens.stylex";

const styles = stylex.create({
	panel: {
		backgroundColor: tokens["--surface"],
		borderRadius: tokens["--radius-md"],
		padding: tokens["--space-4"],
	},
});
```

## Precedence

Component defaults and variants → broad shorthands → axis props → edge props → caller `style`.

`reverse` combines with the rendered component's default axis: vertical roots reverse to `column-reverse`, while horizontal roots such as Card Footer reverse to `row-reverse`. It changes visual order only; semantic and keyboard order remain DOM order.

```tsx
import { Box, Button, Card, CardContent, Grid, Stack } from "@/components";

<Stack gap={4} orientation="horizontal">
  <Card flexGrow={1} shadow="lg">
    <CardContent>Flexible card</CardContent>
  </Card>
  <Button width="full">Continue</Button>
</Stack>

<Grid columns={4} gap={3}>
  <Box columnSpan={2} p={4} radius="md" bg="surfaceSubtle" />
</Grid>
```

## Responsive layouts

Keep all breakpoint values for a CSS property together in a predeclared StyleX style, then pass that complete set through `style`. This follows StyleX's responsive-composition guidance and keeps generic theme props from becoming a second styling system.

```tsx
const styles = stylex.create({
	featureCard: {
		gridColumn: {
			default: "span 12 / span 12",
			[breakpoints.md]: "span 6 / span 6",
		},
	},
});

<Grid columns={12}>
	<Card style={styles.featureCard}>Responsive span</Card>
</Grid>;
```

Prefer fluid flex/grid behavior when it expresses the layout. Promote a repeated responsive set into a named recipe or component variant rather than accepting arbitrary breakpoint objects.

## Escape hatch

Use `style` for a component-local property that is intentionally outside the theme-prop contract. Because it composes last, it wins over defaults and theme props. Promote a repeated, multi-consumer need into the typed theme layer only after its values and ownership are clear.
